My First Open-Source Pull Request

The goal

After the portfolio site, I wanted a next project that would push me past "I can build something from scratch" and into "I can work inside someone else's codebase." Fixing a real bug in an existing open-source project felt like the right next step — it forces you to read code you didn't write, understand why it's structured the way it is, and change it without breaking anything else.

The first target wasn't actually a bug

I started with sharkdp/bat, a popular syntax-highlighting replacement for cat, and picked issue #1618, a "good first issue" about --list-themes breaking when combined with certain pager settings. Before writing any code, Claude cloned the repo, built it from source, and reran the exact reproduction steps from the issue. It was already fixed on main — fixed years ago, in fact. Nobody had gone back to close the ticket, and eight or nine other contributors had independently "discovered" it was still open and submitted duplicate fixes that never got merged or cleaned up.

That was a genuinely useful dead end. A "good first issue" label doesn't mean the issue is still open, and it doesn't mean the label is being maintained. Verify against current main before writing a single line of code, or you risk adding to a pile of duplicate work nobody asked for.

Finding a real one

I pivoted to sharkdp/fd, a fast alternative to find, from the same maintainer. The two issues actually labeled "good first issue" there turned out to be broad, open-ended tracking tickets rather than small bugs — one about building out an entire benchmark suite, one an umbrella "general refactoring" discussion. Not what I wanted for a first PR, so instead of trusting the label, Claude scanned fd's full list of open bugs and checked which ones didn't already have a stack of unmerged duplicate pull requests attached to them — the same pattern that had burned the first attempt.

That turned up issue #1985: fd can't handle arbitrarily deep directory trees the way GNU find can, because it constructs full file paths and eventually hits the operating system's path-length limit. The complete fix for that needs changes to fd's underlying dependencies, which was too large a first PR. But buried in the issue discussion was a smaller, genuinely unclaimed piece of it: fd was silently exiting with a success status even when it hit that error, so any script or tool checking fd's exit code had no way of knowing the search hadn't actually finished.

The fix

Claude traced the error-handling path through fd's source and found three separate places — normal output, the --exec flag, and the --exec-batch flag — where a filesystem error was received but only ever optionally printed, never actually reflected in the program's exit code. All three got fixed to report failure when that happens, even when the error message itself isn't shown.

Proving it actually worked

This is the part I paid the most attention to, because it's easy to assume a fix works just because the code reads correctly. Claude built an unpatched and a patched binary side by side and reran the exact failure scenario from the issue against both — watched the exit code actually flip from success to failure. Then it wrote an automated regression test for the fix, and in doing so caught its own mistake: the test relied on removing read permissions from a directory, but it was running as the root user in its own sandbox, and root ignores permission bits. That made the test pass no matter what it was testing. Claude had to set up a separate, non-privileged user account just to confirm the test genuinely failed against the old code and genuinely passed against the fix. The full test suite, a formatting check, and a linter all came back clean afterward.

The line I didn't cross

My first thought was to just have the whole thing pushed for me automatically. That's where I hit a boundary I actually agree with: no AI assistant should ever be handed a raw GitHub token or password, even if I explicitly offer one. The workaround wasn't really a workaround — Claude prepared the fix as a ready-to-go local repository on my own computer, and I ran the actual git push myself from my own already-authenticated terminal. In hindsight that's obviously how it should work. I don't want to build a habit of handing credentials to a chat window just because it would have been one step faster.

The project's own contributing guide reinforced the same idea from another angle: it requires disclosing AI assistance in a pull request description, and requires that the actual human contributor — not the tool — understands and can defend the change. That felt right even before I read it. I made a point of understanding every line of the diff before pushing, not just trusting that passing tests meant I was done.

Where it landed

The fix is pushed to my fork on a dedicated branch, and I wrote and opened the pull request myself, in my own words, disclosing exactly how Claude was used. Whether it gets merged is now up to the maintainers — but the process of getting there taught me more than a clean merge would have on its own: how to tell a real bug from a stale label, how to verify a fix instead of trusting it, and where the line sits between using a tool well and outsourcing judgment I should keep for myself.
