Your ping sweep is lying about what's on the network

A tool that crashes is annoying. A tool that returns a confident, plausible, wrong answer is dangerous, because somebody acts on it. Network inventory is squarely in the second category: the entire point is to tell a client what exists on their network, and the output only has value if it can be trusted.

I built one — a PowerShell tool that sweeps an authorized range, cross-references what it finds against Active Directory, and reports the gap. Devices answering on the wire with no AD account. AD accounts for machines that no longer exist. Accounts that were disabled on paper but are still running.

Four separate bugs during that build made it quietly wrong. None of them threw an exception. Every one produced output that looked completely reasonable.

Lie one: the sweep skips the machines you care about

The obvious way to find live hosts is the one everyone writes first:

This is wrong on a corporate network, and it is wrong in the worst possible direction. Windows Firewall blocks inbound ICMP echo by default on the Domain profile. A domain-joined workstation sitting right there, powered on, logged in, will not answer a ping.

So the sweep comes back, reports thirty devices on a network that has sixty, and reports it without a warning, without an error, without any indication that half the estate declined to respond. The missing machines are not flagged as missing. They were never candidates.

The fix is to treat silence as unproven rather than as absence, and re-probe every non-responder over TCP:

A host that refuses ICMP but accepts a connection on 445 is not ambiguous. It is a Windows machine with its firewall configured the way Microsoft ships it.

An inventory that silently omits half the estate is worse than no inventory, because someone will trust it.

Lie two: the subnet math was garbage, silently

To scan a CIDR range you need a netmask. The standard way to build one is to take all ones and shift:

PowerShell parses the literal 0xFFFFFFFF as a signed 32-bit integer. It is not 4294967295. It is -1:

Every mask built from that literal was wrong, which meant every network address, every broadcast address, and every enumerated host range was wrong. There is a second trap stacked underneath it: shifting a 32-bit value by 32 is undefined, so a /0 wraps around to all ones instead of collapsing to zero.

I only found this because I installed PowerShell and ran the module before building anything on top of it. Had I trusted it and moved on, the failure would have surfaced later as "the scan found fewer machines than expected" — which is indistinguishable from lie one, and would have sent me hunting in completely the wrong place.

Lie four: the one the tests could not see

The suite is 72 tests. It covers the subnet math, the authorization boundary, every reconciliation path, and HTML escaping. All green.

Then somebody looked at the report and asked why the text on the right was cut off.

nowrap is correct for an IP address or a MAC — those must never break mid-value. I applied it to every monospace cell, including the open-ports column, which holds things like 80/HTTP, 443/HTTPS, 515/LPD, 9100/JetDirect. Forced onto one line, that column shoved the table past its container and pushed the final Status column — the one carrying the actual finding for each device — off the right edge entirely.

No test caught this and no reasonable test would have. The tests assert what is in the document: the right rows, the right values, hostile input escaped rather than rendered. Layout is what the browser does with that document afterwards, and asserting on it means asserting on rendered pixels.

The check that found it was rendering the page headless and looking at the image. That is worth building into the loop for anything that produces a visual artifact, precisely because it catches the class of bug that structural assertions cannot reach.

The thing I got right on purpose

One decision was made before any of that, and it is the one I would defend hardest: the scope check fails closed.

Every target range is checked against an explicit authorized list before a single packet is sent. An unconfigured tool scans nothing rather than everything. A range that only partially overlaps an authorized scope is refused outright rather than quietly clipped to the permitted half. And a hard cap on how many addresses one scope may expand to turns a /8-instead-of-/24 typo into an error message rather than a sixteen-million-address sweep across somebody's WAN.

Scanning address space you were not asked to scan is not a bug you apologise for. It is the kind that ends an engagement, and on the wrong network it is the kind that involves lawyers. The tool refuses in every ambiguous case, because there is no version of "I guessed and got it right" worth the version where I guessed wrong.

The general shape

Every one of these four bugs produced output. None of them produced an error. The scan returned a device list, the reconciliation returned findings, the report rendered, the run exited zero.

That is the failure mode worth designing against in anything whose output someone acts on. A crash is self-reporting — it tells you precisely where to look and it is impossible to ignore. A plausible wrong answer recruits the reader into the mistake, and the more polished the output looks, the more thoroughly it does that. My report had summary tiles and severity badges and a clean layout while it was telling the reader that every machine in the building was simultaneously missing and unidentified.

Which leads to the rule I would keep from this: decide what your tool does when it does not know. Silence from a host is not absence. A name that does not match is not proof of a stranger. An empty configuration is not permission. Every one of those is a place where the code has to choose between reporting uncertainty and inventing a confident answer, and the default in most code is, quietly, to invent one.

Probe twice. Normalise before you compare. Fail closed. Look at the output.

The tool described here is ad-inventory, a read-only PowerShell network inventory and Active Directory reconciliation tool. It ships with a demo mode that generates a full report with no network or domain required. All four bugs above were real, found while building it.
