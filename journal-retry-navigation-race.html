Your retries are hiding a navigation race

There is a specific kind of broken test suite that never shows up as broken. It passes. CI is green. But nearly every run quietly burns a retry on the same step, and the reason it needs that retry is a real race condition that will eventually bite you somewhere retries cannot save you — a duplicate write, a double-charged customer, a job that reports success having done half the work.

I hit this building a demo harness for exactly this class of problem. The bug is small, the cause is genuinely non-obvious, and the reason it stayed invisible is the interesting part.

This is an extremely common pattern — post an action, reload to show the new state. No framework, no client-side router, just a POST and a reload.

The automation drives it in a loop: read how many items remain, click the button, wait for the page, read again. The obvious code looks like this:

That middle line is wrong, and it is wrong in a way that reads as correct.

Why it is wrong

waitForLoadState("domcontentloaded") does not wait for the next navigation. It waits for the current page to have reached that state — and the current page reached it a long time ago. The promise is already satisfied at the moment you call it.

So the real sequence is:

  • Click fires. The handler calls fetch(). The request is in flight.
  • waitForLoadState("domcontentloaded") resolves immediately, against the old page.
  • Your next line reads #status — still the old page, or worse, mid-teardown.
  • Then the fetch resolves and location.reload() finally starts.

The line you added to make the code safe is a no-op. Worse than a no-op: it is a comment that lies. Anyone reading it — including you in three months — sees a wait and assumes the navigation is handled.

What you actually get is a read racing a navigation that has not started yet. Sometimes the read lands on stale content. Sometimes it lands mid-navigation and throws Execution context was destroyed or frame was detached.

Why nobody noticed

Because the step was wrapped in a retry with backoff, like every other step.

Attempt 1 throws. The runner logs a warning, sleeps 400ms, tries again. By attempt 2 the reload has long since finished, the page is stable, the read succeeds. The step passes. The loop continues. The run exits 0.

A retry that turns a red into a green is a bug report you threw away.

The information was there — in the retry counter, in a log line nobody reads, in a run that took noticeably longer than it should have. But the only signal the suite emits is pass/fail, and it said pass.

This is the actual failure mode of defensive retry logic. It does not hide flakiness, it hides causes. The flakiness is still there. You have just removed your ability to find out why.

The fix

Do not wait for a lifecycle event. Wait for the postcondition that means the work actually happened:

Capture the state before the action, then wait for it to change. This is correct regardless of how the page updates — reload, fetch plus DOM patch, client-side route, WebSocket push. It does not care. It waits for evidence that the thing you asked for happened.

Lifecycle events describe what the browser is doing. Postconditions describe what your job needs. Those are different questions, and most wait bugs come from answering the first when you meant to ask the second.

The #signin short-circuit is worth a note. If the session expired, the click bounced you to a login page and #status will never change. Without that check you sit there until the timeout, then burn the whole retry budget on a condition the surrounding loop already knows how to fix. Bail out in one attempt and let the caller re-authenticate.

The second bug hiding behind the first

Once the race was fixed, a different lie surfaced. The run started reporting "target unreachable" after every successful item.

The problem: when a page calls location.reload() on itself, any navigation you had in flight is aborted, and Playwright reports ERR_ABORTED. That looks like a network error. It is not one. It is the page doing exactly what it was built to do.

So a healthy run was declaring an outage on every success — and because the supervisor's job was to restart on outages, a working system was being restarted for working.

The fix is to name the benign cases explicitly rather than letting them fall through:

An explicit deny-list beats "it was not in the allow-list, so it is fine." The next person to extend CONNECTION_ERRORS carelessly gets caught by the deny-list instead of silently reintroducing the bug.

And when you unit-test this, the negative cases are the ones that matter. Any implementation returns true for ECONNREFUSED. The bug was returning true for an aborted navigation. That is the test that would have caught it.

How to tell if your suite has this

Three cheap checks:

  • Count retries, not just failures. If a step passes on attempt 2 more than very rarely, you do not have a flaky environment — you have a race with a bandage on it. Emit the attempt count as a metric and put a threshold on it.
  • Grep for waitForLoadState immediately after a click. Every instance is suspect. If the click triggers an async action that navigates later, the wait is a no-op.
  • Run once with retries disabled. Whatever fails is what your retry logic has been paying for. That list is usually shorter and more interesting than people expect.

The general shape

Retries are for things that are genuinely transient and outside your control: a dropped socket, a rate limit, a cold cache. They are not a substitute for knowing when your work is done.

Every retry added without understanding what it catches converts a loud, cheap, reproducible failure into a quiet, expensive, intermittent one. The suite gets greener and the system gets less knowable. Eventually something breaks in production, and the test suite — which has been silently failing and recovering for months — has nothing to tell you.

Wait on postconditions. Classify errors honestly. Count your retries.
