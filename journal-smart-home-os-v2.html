Building a Smart Home OS on a Raspberry Pi

The goal

After the portfolio site and the open-source PR, I wanted a project with real scope — something that would run continuously on actual hardware instead of ending at a single deploy. So I started building a smart home platform from scratch on a Raspberry Pi: not a hub product wrapped around someone else's cloud, but my own OS-level layer for devices, automation, and control.

The core: an MQTT device layer

At the heart of the system is a device abstraction built on MQTT, using a simple, consistent topic convention — home/<id>/state for reporting, home/<id>/set for commands — so any device, real or simulated, plugs into the same interface. On top of that sits a device manager, a simulated device fleet for development and testing, and a Flask dashboard for monitoring and control. Because the topic convention is the entire integration surface, swapping a simulated light for a real one never means touching the core system — only a config file and whatever bridges the real hardware onto those two topics.

A real rule engine, not just "if this then that"

The automation engine supports multi-condition rules with AND/OR logic, time-of-day windows, and delayed actions with debounce (cancel_if) so a rule can wait before firing and bail out cleanly if conditions change in the meantime — the classic "turn the light off 5 minutes after motion clears, but cancel that if motion comes back" pattern.

Getting boolean combinator logic right turned out to be deceptively easy to get subtly wrong — an AND that silently behaves like an OR compiles fine and passes the first couple of tests you eyeball. That happened to me for real: a chained comparison bug made a configurable AND/OR combiner always evaluate as OR, regardless of what the config said. It read like working code. Instead of just patching that one spot, I turned catching it into a reusable, truth-table-driven verification routine and ran it across the automation dispatcher, the auth layer, the notification channel dispatch, and later the config editor's validation logic — enumerate every case, check both sides of every conditional, and don't trust a boolean expression that takes more than a couple seconds to parse.

Security and remote access

The dashboard sits behind session-based login authentication, with credentials stored as a salted hash and never committed to git. Remote access runs over Tailscale rather than exposing anything to the open internet — no port-forwarding, no public attack surface. Both are confirmed working in daily use on the actual Pi, not just tested locally.

Persistence and notifications

Device and automation history now persists to SQLite instead of living only in memory, so the dashboard's activity log survives a restart instead of resetting to empty. Automations can also trigger real notifications over push (ntfy.sh) or email, independently configurable, with the SMTP password kept out of git entirely. I verified all of this survives an actual service restart on the Pi — state and history come back intact rather than resetting.

A Settings GUI, so the YAML stays out of the way

Up to that point, every config change — adding a device, writing an automation rule, wiring up notifications — meant hand-editing YAML over SSH. I built a full Settings GUI on the dashboard to replace that: a rule builder covering triggers, conditions, AND/OR logic, device and notification actions, delay, and cancel_if, plus device/room management and notification settings — including safely handling the SMTP password across three distinct states (leave it alone, clear it, replace it) so it's never echoed back to the browser once saved. Every save is validated server-side before anything touches disk, and every save still requires a service restart to apply — a deliberate choice, not a missing feature, since a system that always reads its config once at startup is a lot easier to reason about than one where some changes apply live and others don't.

I tested the whole flow end-to-end in a real headless browser: adding a room and device, building a notify-only automation, toggling on push notifications, confirming everything survives a reload, and confirming the backend actually loads what the GUI writes.

Real hardware, finally

Everything up to this point had been proven against a simulated device fleet. The real milestone this week was getting an actual Zigbee coordinator — a Sonoff Zigbee 3.0 USB Dongle Plus V2 — talking to the system for the first time.

The install path (Zigbee2MQTT via pnpm and Node 22, bridged into the same MQTT topic convention as everything else) was ready and had been for a while, but the coordinator itself surfaced one good debugging story: Zigbee2MQTT's config validation errors were unhelpfully generic ("configuration is not valid," no further detail), and separately, the dongle needed its adapter type (ember, for its EmberZNet firmware) set explicitly — auto-detection isn't fully reliable for Ember/EFR32-based coordinators, and the same USB-to-serial bridge chip gets reused across coordinator models that need different adapter values, so it can't be inferred from the USB ID alone. Once diagnosed, the fix was a one-line config change. The coordinator is now live: firmware confirmed as EmberZNet 7.4.4, connected to MQTT, frontend up, ready to pair real devices.

What's next

Two threads: pairing actual Zigbee devices (bulbs, sensors, plugs) now that the coordinator's proven out, and a new direction I'm starting to scope — relay-based control for things like a garage door or gate opener. The right hardware for that turns out to be a dry-contact relay (not a general-purpose smart switch — garage door control boards are low-voltage and expect a momentary contact closure, the same signal as a physical button press) paired with a separate contact sensor for actual open/closed state, since the relay alone only knows it fired a pulse, not what happened after. Both device types slot into the same home/<id>/state / home/<id>/set convention everything else already speaks, and the contact sensor plugs straight into the existing automation engine for free — "notify me if the garage was left open" is just another delay + cancel_if rule, no new engine logic required.

Stack: Raspberry Pi, Python/Flask, MQTT, SQLite, systemd, Tailscale, Zigbee2MQTT.
